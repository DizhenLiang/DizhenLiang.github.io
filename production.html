01 / The Flywheel

飞轮：五个环节咬合。

每一轮都把「失败」变成下一轮的「数据」。没有一次性脚本，只有持续变强的机器。

01

任务定义

把模糊需求翻译成可验收的任务：边界、约束、验收标准。任务本身是可执行、可复现的工件，不是一句话。

02

隔离工作区与沙箱

每个任务一个干净工作区（工作区已抽象成 provider：mount/read/write/list/commit/unmount 一套接口、三后端并存——默认 git-worktree、评测面可选 overlay、LayerFS 需 env 驱动且因 hostPath === false 被评测 harness 显式拒绝，实测倍数与代价见优化页）；智能体生成的代码在 OpenSandbox 容器沙箱里执行，sandboxed 控制面默认 gVisor（runsc），runc / docker 备援，设了 E2B_API_KEY 时走 E2B 微 VM。上一轮的残留不会污染下一轮。

03

智能体执行

Temporal 是唯一执行权威：child workflow 并行扇出，副作用靠 workflowId = 幂等键 + REJECT_DUPLICATE 保证恰好一次，崩溃后由重放恢复。线上实跑的是 workflows/agentLoop.ts；三段式 Plan-Execute-Review 已接线但默认不启用（见下）。

04

独立评测

评测跑在只读、限定 cwd、断网的工具环里，不触生产 workflow；评分按五种方法范式的 rubric，扣分点尽量锚到 file:line，锚点缺失即 fail-loud。

05

数据回流

轨迹、指标、经验回流成下一轮的任务与规则。跑得越多，飞轮越稳。

02 / Runtime

运行时：一个执行权威，一道入口守卫，一份角色库。

不是一组写死的角色，而是以 Temporal 为唯一执行权威的运行时。下面每一项都标了源码位置，也包括我目前没做到的部分——比如 36 个角色库还只在 IDE 侧，运行时没有接。

Temporal 执行权威

恰好一次副作用

apexBranch 用 child workflow 并行扇出（workflows/branch.ts:269-350），扇出由 MCP 的 apex.delegate 工具发起（tools/fastmcp-server.ts:192）；副作用靠 workflowId = 幂等键 + REJECT_DUPLICATE 收口，崩溃恢复由重放提供。apexAgentLoop 同样以 startChild 把写操作交给 apexSideEffect 子工作流（agentLoop.ts:256）。

编排形态

三段式编排：线一直是齐的，缺的是有人按下开关。

规划—执行—复审这条链早就接好了，却零流量。查下去，根因不是缺实现，而是没人发出那个触发字段：两个分发点各要一个请求字段，全仓三个桶（运行时 / 脚本 / 测试）数下来，0 处发出。一个写了却没人按的开关，和没写，在线上是一样的。

2026-11-02 起缺省不再写死回落：run 入口由一个零大模型参与的纯函数路由器按请求信号判单循环还是全拓扑，判定和理由逐条落事件日志，一键可回旧基线。随后又往下接了三层——座位级模型、执行器作为一张有名字的 worker agent、以及「要不要起 worker」的纯函数判定。

但同一套取证标准也回头量了它的定价：押的那一格复算下来点估计为正、没过显著性，代价却是实测的。⇒ 机制已经在生产上分流，定价还没跑赢证据。下面的抽屉是这一节全部的复算入口。

证据 · 接线、定价与派发面的逐条口径

接线位置：三段式编排 workflows/planExecuteReview.ts:323，第三座位（reviewer 复审）activities/reviewStep.ts:55，worker 均已注册。两个分发点要的字段：framework:"plan"（选哪条编排）与 executionMode:"orchestration"（走编排而非单循环）。2026-11-02 起，run 入口 pi-agent/run/route.ts:348 调用纯函数路由器 lib/paradigm/topology-router.ts:158，判 SOLO（单循环）或 FULL_TOPOLOGY（planner 与 reviewer 座位启动）；APEX_TOPOLOGY_ROUTER=off 一键回旧基线，shadow（影子模式）只记录不改行为。

定价：分档阈值 T_SIMPLE=30 是未校准的代理模型，校准样本（估算轮次 vs 该次运行的真实步数）正在攒。FULL_TOPOLOGY 那格回台账复算 +0.083、精确置换 p=0.625（6 对配对，主台账）——点估计为正但未过显著性；代价实测：处理臂 prompt token +71%、轮次 45→59。

2026-11-03 的三层：① 座位模型——三张座位（planner 规划器 / executer 执行器 / reviewer 评审器）各配各的模型（APEX_SEAT_MODEL_*），env 只在入口读一次，再分别以 planModel / reviewModel（plan 臂）与 model（agent 臂）进 workflow INPUT；不在工作流里读 env——那是沙箱违例，且宿主与 worker 容器档位不同 ⇒ 重放可能翻成另一个模型。env 不配 ⇒ 座位字段一个都不进，模型逐字沿用本次 run 的 model。② 执行器是一张有名有姓的 worker agent——SEAT_WORKER_ROLE 把座位映射到执行侧已有的角色规格（Manager / Executor / Critique，不另造角色表），agent 臂两条起跑路径都带 role:"Executor"，agentStep.ts:385 据此把 RoleSpec 契约（职责 / 不负责什么 / 输入输出 / 完成定义 / 交接规则）注进决策系统提示词。这一处没有「逐字节一致」可讲：座位模型缺省同形，角色块却是默认开启的提示词变更（改造前该字段为空，走 emergent 无预设角色兜底）。③ 「要不要起 worker」的纯函数判定 src/lib/router/worker-lifecycle.ts:72（8 项测试）：三选一 answer_only | maintain | spawn——内容没变不起，同一张座位已挂着就维持（重复起跑 = 重复付费 + 重复写）；模型只参与「要几张座位」，不参与「要不要起」。

运行时证据与它的边界：tests/temporal-seat-dispatch.integration.ts 用 @temporalio/testing 的 createLocal 起临时 dev server 跑真工作流（活动全 mock、断言只看活动收到的入参 ⇒ 不花一次补全、不落盘、不需要 Docker），证明规划器活动真收到 planModel、评审器活动真被调用（复审启动不是只写预算字段）、两个 env 都不配时各自回落 run 的 model、执行器活动收到 role=Executor 与座位模型。但这条 integration 不在 GUARDS 的 74 条里 ⇒ 不进 npm run verify，得手动 npx tsx 跑。

派发面的准确形状：decideWorkerLifecycle 除自身测试外零生产消费方，worker 的起跑派发函数（dispatchProjectWorkers）全仓零定义 ⇒ worker 那一面目前只有判定。相对地，建项目派发层已经接线：src/lib/router/provision.ts 用既有六步 helper 建项目并把本轮会话绑上（项目键由消息的幂等种子做 sha256 ⇒ 同一句话重跑派同一个键，不多开项目；失败以 { ok: false } 返回、绝不抛出，由调用方决定回落到哪个项目），被分诊管线 src/lib/feeds/task-pipeline.ts:217 在 new_project 判定上调用，但门 APEX_ROUTER_AUTO_CREATE_PROJECT 缺省关 ⇒ 关时判定只写进任务体，活仍留在给定项目里。另两道按数据切流的门：APEX_ROUTER_ASSESSMENT（AI 研判，阈值 0.5 未校准）与 APEX_ROUTER_SIDEBAR（项目路由），都缺省 shadow ⇒ 只落日志、不改入口行为。所以准确说法是「座位与建项目的派发面已接线、门缺省关；worker 起跑面仍只有判定」——既不是「整条执行面都没写」，也不是「已经生效」。改动要吃到还差进程一侧：座位模型经 INPUT 传递、worker 不读 env，但工作流与活动代码仍需 worker 进程重启才生效（dev 是 tsx 直跑源码，重起即生效；容器化 worker 要重建 bundle），而本机 Docker 引擎 2026-11-03 早间无响应、午后 15:0x 复测已响应（Server 26.1.1）——但 :7233（Temporal 服务端口）的环回位被 @temporalio/testing 的临时 dev server 占住，所以"容器真的在取活"这条仍未被独立取证。

36 个 specialist 定义

角色库，尚未接入运行时

.claude/agents/ 实测 36 个定义（analyst / architect / executor / planner / verifier / reviewer / debugger …）。诚实边界：src/ 对它零引用，当前是 Claude Code / IDE 侧角色库，不是运行时里被动态调起的池子。

四条编排面分清
线上在跑：apexAgentLoop（workflows/agentLoop.ts，路由判 SOLO 时的落点）。按判定起跑：apexPlanExecuteReview——2026-11-02 前是「接线齐备、零流量」，现在由路由决定是否启动 planner/reviewer 座位。PoC、src 零调用：apexOrchestrator（orchestrator.ts，TC-07 单步，文件头自陈「NOT a production candidate」）。只在评测 harness：planner→executor→reviewer 三角色的写权拓扑在 scripts/paradigm-ab-executor.ts，src/ 对它零调用——那是评测面的实验处理，不是运行时功能；生产侧的 reviewer 只有读权，不改实现、只提缺陷。
这条分流是怎么被证明的

我没有只靠读代码就宣布它在分流——打了两个真实请求体进同一个 run 入口：一句短问答被判成单循环，一个带工作区的多步任务被判成全拓扑。后一条的 History 里能看到它自己收口的样子：两步执行、两轮复审、一次返工——第 1 轮复审输出不是合法 JSON，按「失败闭口」记为不通过并带原因；规则判定还剩一个名额，于是放给 planner 返工一步，第 2 轮给出六条具体缺陷，名额用尽即收口。

这条链证明的是机制，不是效果：planner 两步决策都是 done 且答复为空，交付没落地——是复审把它抓出来的，而抓到缺陷不等于修好了缺陷。

证据 · 两个请求体的返回、id 与缺陷清单

短问答（无落点工作区）⇒ 判 SOLO，返回 framework:"agent"、工作流 id 前缀 agent-loop:、复审字段为空。「重构登录 + 补单测 + 跑回归 + 出覆盖率报告」并带工作区 ⇒ 判 FULL_TOPOLOGY，返回 framework:"plan"、workflowId=plan-exec-review:entry-live-full-…（Temporal 历史可查，2026-11-02 18:39 本地收口 COMPLETED）。

循环上界因此是 maxSteps + reworkSteps。第 2 轮复审的六条缺陷逐条为：没动 site-users、没动路由、没加测试、没跑回归、没出报告、动作序列为空。

入口守卫
dispatchIngress：默认拒绝的白名单单接入点，外部流量只经它直交 Temporal，不中转、不在入口扇出。
单写权威（TC-11）
业务只写 Temporal 一处；PostgreSQL 是可由 History 重建的 CQRS 读模型，Temporal 不可达时 fail-closed，绝不静默回退 PG。
03 / Isolation

隔离：执行进沙箱，评测走只读工具环。

执行面管「能不能跑」，评测面管「算不算对」。两者是不同性质的约束——我不把它们说成「物理隔离的双沙箱」，因为评测侧目前是进程内的只读工具环。

执行沙箱
OpenSandbox（阿里，Apache-2.0）容器隔离：智能体生成的代码跑在容器里，sandboxed 控制面默认 gVisor / runsc，trusted 层 runc，docker 为声明的备援，设 E2B_API_KEY 时走 E2B 微 VM。出处 opensandbox-client.ts:4-11、exec-safety.ts:14。
评测面
只读工具集 + 限定 cwd + 断网的 worktree 工具环，刻意不触生产 Temporal workflow（paradigm-ab-eval-skeleton.ts:38）；Harbor 任务契约是 agent → environment → verifier → reward.txt，模式 spawn / latest（harbor-eval-bridge.ts:11-12）。
隔离收益
防跨任务污染、防「改评测器过题」、防止评测动到在飞的生产 run；代价是过程指标只能先走 proxy 口径（见评测页）。
04 / Self-healing

自愈 · 巡检 · 熔断。

长任务最怕的不是报错，是「静默错误」——跑完了，但结果是错的。下面三层兜底把它提前暴露；阈值都按代码里的真实值写。

自愈

重放 + 幂等 + 分级重试

核心 run 用 maximumAttempts = 1：不盲重试，靠 Workflow 重放与幂等键恢复（workflows/piRun.ts:49）；agentLoop / Plan-Execute-Review 是 3 次，cron 任务 2 次。没有笼统的「最多重试 2 次」。

卡死收口

claim TTL + 超时，不是 watchdog

任务级回收靠 claim TTL 15 分钟、心跳陈旧 1 小时、崩溃检测 30 秒 + Temporal runTimeout（hermes-kanban/constants.ts:66-79）；apex-worker-watchdog.mjs 只做 worker 进程级保活重拉。

巡检与守卫

26 项守卫 check · 74 条守门清单已入库

judge 完整性 26-check 覆盖「分数缺失、理由为空、锚点不存在、阶段跳过」四类静默缺陷；巡检与守卫脚本合计 1,523 行，本身被测试覆盖。仓内记录的最近一次全量实跑是 AGENTS.md 里的 67/68 通过（1 条依赖 Temporal / Docker 外部栈），当时清单还不足 70 条——清单会长，而且「条数」有三种口径（2026-11-03 傍晚实测：HEAD 的 GUARDS 数组 74 条——clone 后能复算的就是它；同日工作树读数 77→78→79，多出的 5 条登记还在并发会话的在飞索引里未入库；元门禁 guard-coverage 报 78 是第三种口径，79 条里 1 条不在 tests/ 下），所以通过率的日期和口径比数值更要紧。也别把「进了 GUARDS」当「跑过了」：tests/temporal-seat-dispatch.integration.ts 这类真工作流证据目前不在那 74 条里，只能手动跑。反过来也别把批量里的一次红当回归：同日 guard-coverage 报 5 条「没被认领」，可同一轮它自己刚执行过其中几条——成因是同一工作树里另一会话的一次提交，pre-commit 备份/还原期间把它读的那份源码换成了入库版（半写快照），单跑立刻绿。读源码文件的守卫，红先复跑单文件再谈改代码。

熔断

看板派发器默认连续 2 次

DEFAULT_FAILURE_LIMIT = 2（hermes-kanban/constants.ts:99、dispatch.ts:435），先停、再看、再修。降级路径另有 npm run test:fault-injection 串跑 5 个测试来逼出真实行为：PG 真连不上、ANN+BM25 双 down、ANN down 时 BM25 扩窗、ES 降级、Temporal child-workflow 入口。

05 / Observability

可观测：指标推送 + 时序 + 追踪。

一条轨迹要能回答：哪一步慢了、哪一步错了、哪一行代码导致的。这里只讲已经在跑的面，没跑的不算数。

指标面
prom-client → Pushgateway 推送 → Prometheus 时序（paradigm-ab-metrics.ts:306-309）：任务吞吐、成功率、时延、成本、skill 调用率。
追踪面
Langfuse：LLM 调用链、token、上下文窗口、评分，逐跳可回放；每条 trace 带批次 tag，能按批次 / 任务 / 阶段下钻。
面板层
诚实边界：Grafana 面板已决定退役、改走 Prometheus API + 告警 webhook，但该项在清单里仍未勾选完成；采集与查询层不受影响。第三个声明面是 OTel，不在这里吹成独立平面。
