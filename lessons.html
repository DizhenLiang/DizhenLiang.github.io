01 / Counting

任何计数，落笔前先固定三件事。

求和方式、范围口径、日期。这三件没固定，「审计数字」只会把错数换成另一个错数——我自己踩过四次。

求和方式

xargs wc -l | tail -1 造出一个假数

xargs 会把超长文件清单拆成多批，每批各打一个 total，tail -1 只取最后一批。同一范围这样算只剩 71,506 行；单遍求和的真实值是 258,283 行 / 1,040 个文件（src + tests + scripts，2026-11-02 复算；同一把尺 2026-11-03 傍晚重跑是 269,540 行 / 1,084 个文件——旧那对留着，因为它标的是自己那天的日期）。

凡 xargs … | tail -1 得到的 total 都不可信
行数 ≠ 格子数

10-30 那份「零缺口」结论就是这么来的

两份台账合计 206 行，去重后只有 81 个格子（一个「任务 × 臂」的评测单元）；重复 125 行，重复率 154.3%。只看主台账是 198 行 → 76 个格子。数的是行、宣布的是 cell、中间没有去重步骤，就会报出「全有判分、零缺口」。

取数规则：同一 key 只认最新行，且必须先声明 key 的组成
范围口径

「测试文件 307」和「162」可以都对

差别只在把 .claude/ 里的角色库测试算不算。现在的公开口径一律写清范围：git 跟踪的 *.test.ts / .tsx / .mts = 168 个（2026-11-03 复算；307 / 162 是 11-02 前后的两个历史读数，留着是因为它们演示的就是"口径决定结论"这件事），其中用例声明 1,050 条（只数行首 it()/test()，换定义就不是同一个数）；API 路由 61 个（src/app/api/**/route.ts，复算未变）。口径不写，数字就会被当成立场。

同一指标只在一处定义，别处引用
日期

会自己漂的数必须带复算命令

提交数 10-30 是 1,205、11-01 是 1,206、11-02 是 1,211、11-03 早间 1,243、17:0x 1,250、傍晚 1,253、11-06 复算 1,295——不是我数错，是它在长（11-02 到 11-03 一天 +42 次提交）。守卫清单从 70 条长到 HEAD 85 条（2026-11-06 复算；同日工作树读数 86，多的 1 条 tests/temporal-router-plane.test.ts 未提交；11-03 那次工作树 77→78→79 也是清单当天在长，多出的 5 条登记还在并发会话的在飞索引里未入库；无重复、目标文件全部存在）。同一个「条数」有三种口径，公开页必须说清算的是哪一种，否则读者复算对不上。所以公开页每个数都带日期和一行命令，读的人能自己重跑。

git rev-list --count HEAD = 1,295（2026-11-06）
02 / Evidence Plane

评测的账本，比代码更容易被写坏。

结论可以重算，前提是你手里那份轨迹数据没被悄悄改过。今天中午就抓到一次现场。

现象

台账 mtime 变了，内容一个字节没变

主台账 results-v5-30s-fullredo-20261013.jsonl：修改时间 12:03:18，inode 与创建时间（10-26）都没变，sha256 与 11-01 的快照逐字节一致（68e40f72…）。⇒ 这是打开后整文件就地覆写，不是临时文件改名；写入方是并行会话，不是我这边（我对它只有三次只读探针）。

后果

任何在窗口里读台账的程序都会读到截断

同一条守卫命令在 20 分钟内出现 13 PASS / 0 FAIL → 若干项红 → 13 PASS / 0 FAIL，而期间文件哈希恒定。这不是测试不稳定（flake），是消费者撞上了写入者的覆写窗口。把它记成「环境问题」，下一批数据还会再撞。

修法

原子写 + 每行带 run 标识 + 占位行不得覆盖真判定

三件事：① 写台账改 temp+rename，杜绝中间态可见；② 每行加 runId / attempt（第几次跑）——现在 206 行全都没有，唯一疑似标识重跑同值，导致 4 / 81 个格子的两次 run 塌缩成一行，被藏的早期分数找不回来；③「取最新行」要有权威规则：占位分不得覆盖同 key 已有的真判定。

复算

判「有没有被改」用四个量，不用印象

sha256sum（内容）＋ inode（是否换了文件）＋ birth（创建时间）＋ mtime。只看 mtime 会误报「数据变了」，只看哈希会漏报「刚被覆写过」。

03 / Fail-Loud

断言要能变红——包括守卫自己。

一条永远不会失败的断言不是测试，是装饰。这句话对我自己写的守卫同样成立。

红证

新守卫必须先被改坏一次

本轮把「角色段装配顺序 + 相位写权」钉成 29 项检查（tests/paradigm-ab-role-phase.test.ts，29 PASS / 0 FAIL）。它立项前跑了 8 种改坏：把 reviewer 写权放开、把顺序改回裸正文在前、把交付物路径写歪、去掉 rescue 通道的白名单过滤、把「小缺陷可自修」的提示词加回去、去掉组合臂的并集、把逼写盘的门恢复成不分角色……8 种全部变红，才允许收进 run-guards.mjs（第 338 行）。

改坏只作用于 .omc/tmp 下的源码副本——工作区被多个会话共用，不动真实文件
双向白名单

已知缺陷的豁免清单也会过期

台账完整性守卫带一份白名单，写清当前已知缺陷。多一个缺陷要红，缺陷被修掉后条目没删也要红——否则白名单会退化成第二个没人读的 TODO。

判据同源

报告与 CI 共用同一份纯函数

全量轨迹复算脚本既出报告数字，也导出判定函数（识别占位分、final 未落盘、跨文件同 key、重跑塌缩）。报告的数和 CI 的红不可能漂移，因为不是两套实现。

纯读、零网络、零改台账
假阳性也要防

「全绿」之前先证全覆盖

写「某个字段从没被写过」之前，我先按嵌套路径去测，得到过错误结论；同一字段其实写在行的顶层。规矩变成：报「有问题」前先证伪自己，报「没问题」前先确认探针打在了正确的位置。

04 / Structure over Prompt

在提示词里祈祷模型自觉，已经被实证无效。

要改变行为，就改结构：谁有权写、什么时候必须写、写不进就拒收。四件事，每件都有对应的落地位置。

拒收而非提醒

「没落盘就不算做完」要变成门

有格子跑完整个流程、最终输出很完整，但落盘证据是 NONE——按口径这是零分。此后 final 被接受之前，会拿任务钦定的交付清单对照本次写入台账，缺件就拒收并借一轮。写盘优先的提示只发给该写盘的角色。

分角色

别把审查者逼成第二作者

同一道门最初对所有角色生效，于是审查者被推着去补写它无权改的交付本体：借一轮、被拒、空转。现在每个阶段只被推它自己有权写的东西（executor 不限；planner 只写自己的计划文档；reviewer 只写测试执行报告），缺陷一律以 REWORK 行回流给 executor。

roleWriteAllowance() / roleGetsWriteFirstNudge() —— 均在 scripts/paradigm-ab-executor.ts:2967，src/ 零调用：这是评测 harness 的机制，不是生产运行时功能
写通道内部

检查必须放在真正写盘的那一层

主循环里加判断是不够的：工具走的是通用调用平面，末步还有一条把正文倒灌成文件的补救通道。拒收逻辑下沉到写通道本身，四个补救入口共用同一份白名单。

否则「绕过去」不是漏洞，是默认路径
顺序即语义

角色段要排在任务正文之前

装配顺序原来是「裸正文 → 角色段 → 上游输入」，模型先读完完整任务书、再把角色段当补充说明，分工容易被忽略。现在是角色段 → 裸正文（两臂逐字节同一份）→ 上游输入。buildRoleTurnInstruction() 把这个顺序写成一个纯函数，被守卫锁住。

同一条的另一面
提示词说「你能写」、通道却拒收 = 必然空转一轮。三个角色的系统提示词自述与写权一致性，现在是一条独立的检查项，而不是靠人眼对稿。
改语义的代价
装配顺序和写权两条改变了两个臂的行为，历史格子不能直接和新格子混池比较：读数一律按改动日分桶，路由先验（阶段 → 收益的估计）需要重估。
05 / Statistical Rigor

门槛要在开跑前锁死，不是在出分后解释。

评测最容易自欺的一步，是拿刚好过线的样本宣布结论。

样本量
三个参数定门槛：α=0.05、功效 0.8、最小效应 d=0.5 → 配对检验约需 60 对。为什么留余量：实测剔除率约 50%（缺臂 / 污染 / 假 max-turns）。现在严格键下只有 33 对，所以每个结论后面都跟着「方向性信号，不是可推广结论」。
多重比较
五个阶段同时检验，不校正的话「至少撞上一次显著」的概率约 23%。用 Holm 按 p 值从小到大递减阈值卡，比朴素 Bonferroni 更有功效。
分尺陈述
同一批数据上有两把尺：人工判分与机器判分，它们可以给出符号相反的结论。DP 在人工判分尺上是 +0.153，剔除 6 个作废格子后升到 +0.214——污染量 +0.061 的方向对 DP 有利，所以 +0.153 本身就是被占位 0 压低过的保守值；而在机器判分尺上只有 6 对、−0.167。混在一起报「平均 +0.0X」就是把两把尺折成一把不存在的尺。
预注册
主终点、判据、批次口径在跑之前写进 registration.json，跑完不能改口。这条纪律的价值不在严谨，而在让「事后调整口径」变得可被发现。
06 / Forensics

判断「真的在跑」，只有一条判据：调用方计数。

注释、文档、注册表怎么声称都不算证据；源码里有没有调用方、什么时候被触发才算。

三桶计数

tests 里有断言 ≠ 运行时会触发

任何「部件是否生效」的问题都按三个桶数调用方：src/（真实运行时）／tests/（回归夹具，不算落地）／scripts/（人工触发，不算自动接线）。最常见的误判是把 scripts/ 里的 verify 脚本当成生产链路。

注册成功 ≠ 被分发：能找到 handler 的注册、找不到分发点的调用，handler 永不触发
历史读数

先查它的取证日期，再决定能不能用来定价

注释里「同一份文件被重读 4–14 遍」出自 2026-10-09 的轨迹取证，而截断与白回放两处缺陷 10-14 就修了——那串数字不能拿来给今天的设施定成本。本批全量台账里，死于复读型停止的格子集中在控制臂，不在方法注入臂。

探针自错

工具会静默告诉你「没有」

踩过四类：Windows 下内联脚本经 cmd.exe 执行导致检索类探针静默假阴性；追踪服务的列表接口上限 100，传 1000 会返回空数组而不是报错；目录联接递归删会穿透到真实源码树；MSYS 会把 /run 这类参数改写成盘符路径。

每个探针都要带一个阳性对照，否则「查不到」无法区分「不存在」与「查错了」
外置什么

判定基准可以外置，执行提示不行

把验收契约写进独立文件、让版本历史可 diff，是被验证有效的做法（设计方案文件 14 份全部被 git 跟踪且与盘上一致）。但把它喂给模型当输入，就把判定基准降级成了执行提示——测出来的不再是「履约能力」。

今天的现场案例（含它的后半段）

「已注册 + 有分发点」仍不等于「在生产跑」——但数出来之后还有下一步

被问「三段式编排进生产了吗」，三桶计数加上第四问给出的答案不是是或否，而是一个修复位置：workflow 在 src/ 里有、worker 注册了、API 分发点有两个，缺的是发出触发字段的那一方。于是补的就是那一方——一条零大模型参与的纯函数路由当发出者，缺省不再写死回落单循环，请求信号决定走单循环还是全拓扑，判定连理由逐条留痕，回退只要一个环境变量。

落地当天，两个真实请求体把两条臂都跑了出来，Temporal 历史里可查。同一天，另一份取证把这条分流的定价打了回来：它对外引用的收益数字在现台账复算不出，而代价却是实测的 ⇒ 引用作废，代码注释和对外文案一起改回可复算的数。

教训有两层：数出「缺发出方」只是开头；把发出方补上以后，还要拿它自己引用的数字反查自己。

证据 · 缺的是哪个字段、复算差在哪

缺的发出方：两个分发点各要一个请求字段——framework:"plan"（选哪条编排）与 executionMode:"orchestration"（走编排而非单循环），实测三个桶（src／scripts／tests）发出方均为 0。

定价被打回：路由判 FULL_TOPOLOGY 时引用的「+0.17」出自一份已不在仓库里的批次报告；用现台账独立复算是 +0.083、精确置换 p=0.625（6 对配对），未过大显著性；代价侧实测 prompt token +71%。

补第四问：谁真的发出了那个触发字段——分发点存在 ≠ 有请求方走它
07 / Boundaries

诚实边界不是免责声明，是这个站点的差异点。

每一页都带源码位置和一份「没做到」清单。写清局限的成本远低于被追问出来。

  • 「代码在 src 里」和「在生产跑」是两件事——线上实跑的是路由判 SOLO 时的 apexAgentLoop；三段式 Plan-Execute-Review 自 2026-11-02 起由入口路由决定要不要启动 planner/reviewer 座位（两条臂都有真实请求跑通、Temporal 历史可查），但它所引用的评测效应回台账复算没到显著性（+0.083，p=0.625）⇒「在跑」不等于「跑赢」；三角色的写权拓扑仍只在评测 harness；范式引擎总开关默认关。这一页不用它们讲成「生产已经在用某种方法并因此变好了」。
  • 跳步与返工仍是 proxy 口径——由执行段自己统计，还没接成工作流历史真值；改造方案已写好，未落地，所以列成待办而不是成果。
  • 两条路由别混成一条——评测面那条（scripts/paradigm-ab-router.ts）仍是影子模式：只记录不生效，96% 任务走全拓扑，预估省 43%（454 vs 799 轮）不能当已实现收益；生产入口这条（lib/paradigm/topology-router.ts）2026-11-02 起默认生效，但它管的是「单循环 vs 三段式」，不管范式注入。先验都用的是同批任务，属样本内估计。
  • 组合臂从未起跑——把两种方法叠在一起跑的那条路径，账面上标记字段命中 0 行；本轮只是把它三个会静默失败的前提修掉了。
  • 覆盖缺口比统计缺口更值钱——81 个任务里 41 个从未执行。补配对数的正道是补覆盖，不是把不同语义的格子并池凑数。
  • 审计者自己的新数要用同一把尺复算——上一轮公开页审计抓到四处自己造成的错（假行数、过期断言数、漂移的提交数、误标的环境档位）。产出不是「删掉假数」就完事。

设施的价值不在它跑得多快，而在它出错时你能不能定位——然后把这一次定位，变成下一轮的守卫。
