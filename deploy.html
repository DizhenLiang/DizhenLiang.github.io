01 / Pipeline

启动顺序：七步，其中几步还靠人。

每一步都指到仓库里的真实文件；没自动化的地方我直说没自动化——把靠人的环节逐个变成脚本，才是这张清单的用途。

01

环境准备

Node 22 + Docker 运行时；.env 必填项校验；沙箱控制面就位——OpenSandbox 的 trusted / sandboxed 两份 toml，sandboxed 默认 gVisor（runsc）。

02

依赖安装

package-lock.json + npm ci（Dockerfile:71 与 CI 都强制），禁止隐式升级。已知短板：Python 侧只有未锁版本的 requirements.txt。

03

外部服务分层拉起

docker-compose.yml 起 PostgreSQL / Redis / Temporal / 观测栈；deploy/compose.yaml、compose.dev.yaml、compose.integration.yaml 分档；k8s 清单在 deploy/k8s/agent.yaml。

04

应用与 worker 启动

next dev(:3000) 与 Temporal worker 同进程 co-located。Windows 已知坑：冷重启后 Turbopack 持久缓存会被毒化成瞬时 404，靠 touch-a-route 恢复；dev:stop 曾静默 no-op——这类环境性失败我单独归类，不冤枉代码。

05

启动自报

worker 存在性探针（可 fail-closed，src/instrumentation.ts:56-80）+ /api/apex/metrics Prometheus 端点 + compose healthcheck 探 workspace 路由。注意：仓内没有 /api/health 端点，healthcheck 探的是 workspace 路由。

06

分链路验证

e2e-agent-mode.mjs（真工具调用 + 落盘断言）、verify-chat-stream-e2e.ts、smoke-trust-routing.ts，评测侧再跑执行面自检。诚实边界：没有一条覆盖「沙箱 + 结果 + 指标 + 异常」的统一上线冒烟，package.json 里也没有 smoke 入口。

07

灰度与回退

回退靠 env 旗标切换实现路径（如 KAFKA_ENABLED、L1 legacy ↔ jev-node），runbook 见 docs/g4-jevnode-gray-runbook.md §5。诚实边界：没有一键回滚，也没保留上一版镜像（本地 build、无 registry tag），k8s 是 Recreate 策略。

02 / Assets

配置与资产分层。

这一节只列仓库里真实存在的文件。一个项目「有多少模板」是可数的，所以我不写约数——下面是实数，以及配置化机制没覆盖到的地方。

compose 分层

1 + 3 份 compose，加一份 k8s 清单

docker-compose.yml 是主组合，配 deploy/compose.yaml / compose.dev.yaml / compose.integration.yaml 三份分档，另有 deploy/k8s/agent.yaml。观测栈还有独立的 grafana-public 组合文件（面板决定退役、采集层保留）。

配置化机制

{{repoRoot}} + env 回落链

config.yaml 用占位符注入仓库根，launcher 路径走 env 回落（acp-registry.ts:122-135）。没做到：仍有硬编码绝对路径（project-creation.ts:3 默认 C:\Users、另 4 个脚本写死路径），所以我不讲「零硬编码」。

契约边界

层与层只认契约

执行层、评测层、观测层各自独立：业务只写 Temporal（TC-11 单写权威），评测结果只经 syncEvalResult 一个写口，指标按批次 tag 归组。契约不变，内部可换实现。

环境档位

dev / integration / prod-equivalent

三档 compose 各管一段，同一套代码切配置。没做到：没有独立 staging 档与 .env.staging（docker-compose.yml 只有 profiles: [app]）。全仓提到 staging 作为环境的只有两处注释——deploy/TEMPORAL-WORKER-RUNBOOK.md:140 与 eunomia-middleware.ts:48，其余 staging 字样都是 git 暂存区。

Why it matters

为什么部署值得单独讲。

长任务系统一旦上线，失败成本会被时间放大：跑了一夜才发现环境不对，比跑五分钟就报错贵得多。所以我把启动顺序、清单和回退手段都写成可核对的文件路径，让「环境不确定性」在上线前被消掉一部分。

还有几处没变成机制：统一的上线冒烟单、镜像版本保留与一键回滚、上线前的资源余量校验、把这张清单挂进 CI 做门禁。这一页写下「还没做」，是为了下一步逐条把它做掉——而不是假装它已经存在。
