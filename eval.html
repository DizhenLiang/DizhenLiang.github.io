01 / Pipeline

7 步流水线。

从任务到结论，每一步都有输入、输出、失败处理；任何一步不通过，都不会进入下一步。

01

任务生成与预注册

把需求翻译成可执行任务，主终点、判据、批次口径先写进 registration.json 预注册——跑之前锁口径，跑完不能改口。结果逐行落 results.jsonl，当前实测 198 行。

02

执行面自检

先证明评测没污染生产：指标与 trace 打在独立批次 tag 上，生产面查询计数不因此增长（verify-plane 类自检）。先证明「没串味」，再谈「跑得对」。

03

数据集构建

任务统一成 Harbor 契约：agent → environment → verifier → reward.txt，模式 spawn / latest（harbor-eval-bridge.ts:11-12）。数据集构建侧要求锚点可解析，找不到锚即 FAIL，不静默放行。

04

评测执行

按 DD / PP / DP / VM / CD 五种方法范式各跑一遍。执行段是只读、限定 cwd、断网的 worktree 工具环（paradigm-ab-eval-skeleton.ts:38），刻意不触生产 workflow。

05

指标采集

prom-client → Pushgateway → Prometheus，配 Langfuse trace；批次 tag 贯通指标、trace 与台账，异常 fail-loud。

06

评分汇总

LLM-as-judge 按注册终点出分（DD=problem_coverage、PP=plan_coverage、DP=requirement_coverage、VM=skips+rework、CD=analysis_validity），异步 worker 跑，判据与权重固定，扣分点尽量给出证据指针。

07

数据回流

失败样本回流成新任务与新守卫——比如首跑发现的 4 个假收敛，直接变成了 judge 完整性检查项。评测不是终点，是下一轮的输入。

02 / Data Pipeline

数据管线设施：让评测可复现。

评测最怕「这次过了、下次不过」。数据管线的职责，是把不确定性钉死在契约、隔离、指标、骨架四件事上——每条都写清它实际做到哪一步。

Harbor 任务契约

agent / environment / verifier / reward.txt

任务统一成四段契约：verifier 产出 reward.txt 作为确定性真值，运行模式 spawn / latest（harbor-eval-bridge.ts:11-12）。这份契约的价值是「同一任务在别的机器上重跑，判分口径不变」。

队列与写口

apex-eval + 独立投影表

评测走独立 task queue apex-eval，结果只经 syncEvalResult 单写口进独立投影表 projection_eval_results，PG 不可用即抛。边界：它与生产同 worker、同连接，是逻辑隔离，不是独立部署体。

指标与追踪

推送 / 时序 / trace

Pushgateway 推送、Prometheus 存时序、Langfuse 记 trace 与评分；指标带批次 tag，可按批次、任务、阶段下钻。边界：Grafana 面板退役仍在清单里未勾选，采集与查询层不受影响。

Eval Skeleton

registration.json + analyze.mts

新评测套同一套骨架：预注册（主终点、判据、批次口径）→ 运行 → paradigm-ab-analyze.mts 分析。跑之前把口径锁死，跑完不能改口。

批次与台账

批次 tag + fail-loud + 198 行

每批一个唯一 tag，串起指标、trace 与台账；异常不静默，直接 fail-loud。结果台账 results-v5-30s-fullredo.jsonl 实测 198 行（10-28 报告写作 191，以文件为准）。

隔离边界

只读工具环，不触生产

评测执行只读、限定 cwd、断网，刻意不启动生产 workflow；执行侧的沙箱是 OpenSandbox 容器（gVisor / runsc）。代价是过程指标只能先走 proxy 口径，见下方 judge 一节。

03 / Rubric

五种方法范式，各自一个注册终点。

DD / PP / DP / VM / CD 不是流水线阶段，而是五种工程方法范式（paradigms.ts:10-15）。每个范式只对它注册的终点打分，口径写在 registration.json 里，跑之前锁死。

DD 双钻
problem_coverage：问题空间是否被覆盖——需求里每个问题点有无对应实现、边界条件有没有做到。
PP 金字塔
plan_coverage：计划与结构是否覆盖。「结论先行」是它的子判据之一，不是注册终点——注册口径是 plan_coverage，比单独讲「结论前置」宽。
DP 设计方案引导编码
requirement_coverage：任务描述里的每一条需求是否被满足，逐条核，不靠「整体感觉」。这是当前唯一测出稳定正效应的范式（+0.17，跨 judge 稳健）。
VM W 模型
skips + rework：跳了几步、返工几次。口径注意：注册终点里没有「测试覆盖率」；且当前这两个指标是 executor 统计的 proxy 口径，不是 Temporal History 真值。
CD CRISP-DM
analysis_validity：分析过程是否成立。数据泄漏与可复现是它的子判据，不是它的全部——打分打的是有效性整体，两条子判据各自还有守卫。
04 / Judge Accuracy

评判准确性：judge 自己也得被评测。

如果 judge 会漂、会漏、会编，所有分数都不可信。但 judge 本身是 LLM 调用，不是纯函数——所以要靠守卫与实测漂移来管住它，而不是宣称它天然稳定。

judge 的真实形态

LLM-as-judge，不是零 IO

评分走异步 worker，await callModelFn(...) 真发网络调用（eval-agent.ts:111）。确定性的部分是判据、权重、守卫和回退面，不是 judge 函数本身。

26-check 守卫

四类静默缺陷

judge 完整性测试实数 26 项 check（tests/paradigm-ab-judge-integrity.test.ts），覆盖「分数缺失、理由为空、锚点不存在、阶段跳过」；缺一项就不出分。

残片守卫

防「看起来有分，其实是垃圾」

截断、空证据、错位锚点、越界分数四类残片各有对应检查项，与 26-check 同属一条守卫链，不静默放行。

跨 judge 漂移实测

0 / −0.01 / +0.15 / 0

同批任务换 judge 重跑 4 个 cell：dp-007 双臂漂移 ≤0.01（稳健），vm-018/c 低分端 +0.15（偏严）。诚实边界：n=4，只能说明方向，不能声称全局 ≤0.01。

轮帽

复审 32 轮 / 初审 80 轮

PARADIGM_AB_REREVIEW_CEILING = 32（初审帽 80）。实测识别出 16 / 76 个 reviewer ≥60 轮的失控样本，纳入治理口径但没有剔除——真实失败样本要保留。

教训

首跑 12 cell 中 4 个假收敛

dp-001/t（147 轮重复）、vm-017/c（238 轮强制写入）、dp-015/t（837 轮撞 max-turns）、cd-eval/t（48 轮）——「看起来收敛」不等于收敛，这条教训直接催生了上面的守卫。

05 / Goals

三层评测目标。

评测要回答三个层次的问题：跑不跑得动、跑得对不对、跑得值不值。

可用性
跑得动：任务能进沙箱、能出结果、能在超时内完成；这是及格线，不是目标。
正确性
跑得对：各范式的注册终点（problem / plan / requirement coverage、skips+rework、analysis_validity）达标；正确性不能被「效率」换掉。
价值
跑得值：在正确的前提下，成本、时延、返工率是否可接受；这层决定能不能规模化。

实测结论
DP（设计方案引导编码）是当前唯一测出稳定正效应的范式，配对差 +0.17 且跨 judge 稳健；VM（W 模型）成本最高而无可见增量。但每个范式只有 6–12 对配对样本——这是方向性信号，不是可推广结论。
口径注意
跳步 / rework 现在是 proxy 口径；把它们变成 Temporal History 真值的改造方案已写好（PR E0–E3），尚未落地。这一页把它列成待办，而不是成果。
