01 / Pipeline

7 步流水线。

从任务到结论，每一步都有输入、输出、失败处理；任何一步不通过，都不会进入下一步。

01

任务生成与预注册

把需求翻译成可执行任务，主终点、判据、批次口径先写进 registration.json 预注册——跑之前锁口径，跑完不能改口。结果逐行落 results.jsonl：两份台账合计 206 行，按「任务 × 臂 × 批次」去重后是 81 个格子（重复率 154.3%，2026-11-02 复算）。数行不数格子，会得出「全有判分、零缺口」的错结论。

02

执行面自检

先证明评测没污染生产：指标与 trace 打在独立批次 tag 上，生产面查询计数不因此增长（verify-plane 类自检）。先证明「没串味」，再谈「跑得对」。

03

数据集构建

任务统一成 Harbor 契约：agent → environment → verifier → reward.txt，模式 spawn / latest（harbor-eval-bridge.ts:11-12）。数据集构建侧要求锚点可解析，找不到锚即 FAIL，不静默放行。

04

评测执行

按 DD / PP / DP / VM / CD 五种方法范式各跑一遍。执行段是只读、限定 cwd、断网的 worktree 工具环（paradigm-ab-eval-skeleton.ts:38），刻意不触生产 workflow。

05

指标采集

prom-client → Pushgateway → Prometheus，配 Langfuse trace；批次 tag 贯通指标、trace 与台账，异常 fail-loud。

06

评分汇总

LLM-as-judge 按注册终点出分（DD=problem_coverage、PP=plan_coverage、DP=requirement_coverage、VM=skips+rework、CD=analysis_validity），异步 worker 跑，判据与权重固定，扣分点尽量给出证据指针。

07

数据回流

失败样本回流成新任务与新守卫——比如首跑发现的 4 个假收敛，直接变成了 judge 完整性检查项。评测不是终点，是下一轮的输入。

02 / Data Pipeline

数据管线设施：让评测可复现。

评测最怕「这次过了、下次不过」。数据管线的职责，是把不确定性钉死在契约、隔离、指标、骨架四件事上——每条都写清它实际做到哪一步。

Harbor 任务契约

agent / environment / verifier / reward.txt

任务统一成四段契约：verifier 产出 reward.txt 作为确定性真值，运行模式 spawn / latest（harbor-eval-bridge.ts:11-12）。这份契约的价值是「同一任务在别的机器上重跑，判分口径不变」。

队列与写口

apex-eval + 独立投影表

评测走独立 task queue apex-eval，结果只经 syncEvalResult 单写口进独立投影表 projection_eval_results，PG 不可用即抛。边界：它与生产同 worker、同连接，是逻辑隔离，不是独立部署体。

指标与追踪

推送 / 时序 / trace

Pushgateway 推送、Prometheus 存时序、Langfuse 记 trace 与评分；指标带批次 tag，可按批次、任务、阶段下钻。边界：Grafana 面板退役仍在清单里未勾选，采集与查询层不受影响。

Eval Skeleton

registration.json + analyze.mts

新评测套同一套骨架：预注册（主终点、判据、批次口径）→ 运行 → paradigm-ab-analyze.mts 分析。跑之前把口径锁死，跑完不能改口。

批次与台账

批次 tag + fail-loud + 行数≠格子数

每批一个唯一 tag，串起指标、trace 与台账；异常不静默，直接 fail-loud。结果台账主文件实测 198 行（10-28 报告写作 191，以文件为准），加第二份合计 206 行 ⇒ 去重后 81 个格子。台账行没有运行标识列，实测 4 / 81 个格子的两次运行塌缩成同一行，被藏的早期分数找不回来——这是已立案的待修项，不是读数误差。

隔离边界

只读工具环，不触生产

评测执行只读、限定 cwd、断网，刻意不启动生产 workflow；执行侧的沙箱是 OpenSandbox 容器（gVisor / runsc）。代价是过程指标只能先走 proxy 口径，见下方 judge 一节。

03 / Scenario

按产品场景选方法范式，而不是反过来。

五种范式不是流水线阶段，是五种工程方法。下面每条都写清：适用场景、实测效应与是哪把尺量的（人工判分 / 机器判分）、成本、以及不该用的情形。全量池化的平均差只有 −0.015——不存在「注入了就更好」，收益是场景相关的。

契约化交付
照清单实现
DP（设计方案引导编码）——唯一测出正效应。人工判分尺 meanΔ +0.153（7 对：4 胜 0 负 3 平）；剔除 6 个作废格子后升到 +0.214——也就是说 +0.153 已经是被占位 0 压低过的保守值（污染量 +0.061，方向对 DP 有利）。成本是正效应里最便宜的：+100,035 tokens／对。但必须分尺陈述：同一批在机器判分尺上是 −0.167（6 对，0 胜 1 负 5 平），两把尺符号相反。履约面证据最硬：需求锚点 13/13、追溯表 13/17、交付落盘 17/17。
不该用：任务本身没有可核验清单——dp-015 / dp-016 就是缺设计方案的假前提，属任务集缺陷，不是范式失效。
质量强约束
测试先行
VM（W 模型）——当前不默认注入，值钱的是它的判定面。人工判分尺 meanΔ −0.007（7 对 2 胜 3 负 2 平），却最贵：+2,646,958 tokens／对、轮次均值 137–140。更要紧的是机器判分尺恒 0.000（23 个格子全 0，7 对 0→0）⇒ 现有分数差 100% 来自人工判分。而它的判定资产其实已经到位：任务自带标准答案锚点 17/17，但追溯表 0/24、验收前置 4/17、测试落地 2/17——基准在位、没接线。
修法见下方「DP × W 模型是同类问题吗」；先修的是判定范围（把测试判定收窄到该格子的交付文件），不是提示词。
需求模糊
先定义问题
DD（双钻）——目前证据不支持默认注入。meanΔ −0.086（剔除后 −0.100，7 对 1 胜 5 负 1 平），成本 +247K tokens／对、轮次 25.1→28.7。它的注册终点 problem_coverage（问题空间是否被覆盖）只有人工判分尺，没有机器分可对照，也没有为它建判定基准——这是下一步该补的面，而不是它的失败证据。
早期 10-29 批次曾给出 +0.183 的反向信号，跨批不稳定 ⇒ 只当方向。
汇报文档
短产出
PP（金字塔）在短任务上是纯负担。meanΔ −0.100（6 对 2 胜 4 负，medianΔ −0.20），+152,614 tokens／对、轮次 25.8→30.8、双臂均值 0.775→0.675；单样本实测 pp-004：25 轮 → 61 轮，分数反而下降。控制臂本来就不低（0.775），注入是把它拉下来的 ⇒ 短任务上范式是纯成本，不带来结果差异。
值得用的形态：多层论证的长文档。通用规则（高置信）：轮次中位数 <30 的阶段直接单智能体直跑。
数据分析
口径与效度
CD（CRISP-DM）——唯一「注入后更省钱」的范式，效应中性。meanΔ −0.052（6 对 2 胜 3 负），成本 −1,402,761 tokens／对（比对照臂更省），轮次 84.4 / 88.2。这一场景里真正的强信号不是方法，是有没有写下来：落盘样本均分 0.674，未落盘 0.050（13.5 倍）。
诚实边界：「CD 适合数据分析」在报告里没有直接推荐证据，只有阶段定义——省成本与中性效应是实测，适配性是推断。已知坑：3 个「跑完但没落盘」源自新旧交付契约错配，不是门失效；墙钟实测 37–50 分钟、超默认 25 分钟预算，存在「跑满交空」的前瞻风险。
路由
按复杂度自适应选型的路由实测：DP 走全角色拓扑、其余走单智能体，与上面的场景结论同向。但先验是用同批任务估的（样本内），且 96% 停在只记录不生效的影子模式，预估省 43%（454 vs 799 轮）不能当已实现收益。
03b / Merge

「设计方案引导编码」和「W 模型」是同类问题吗？

成立的部分是机制同族，不成立的部分是任务同族。两种说法后果完全不同：一种会让实验作废，另一种只是把分数打回事实水平。

路线一 · 数据面并池

不作默认

把两者当同一家族配对，能换来的只是配对数 7+7→14；但两臂语义不同（一个是照外部契约履约，一个是自己立验收标准），并池后 +0.214 失去归因对象。而配对数不足的真因是 81 个任务里 41 个从未执行——补覆盖即可，不必凑数。

路线二 · 提示词面合并

禁止

把设计方案文件喂给 W 模型臂，测到的就不再是「自带验证地实现」。前者优势恰恰来自「看不到验收契约、只能去履约」。外置的必须是判定基准（锚点／标准答案），不能是执行提示——喂进去就把它从判定基准降级成了执行提示。

路线三 · 机制层合并

推荐：合并点在判定面

把「基准外置 + 机械可核 + 可 diff」三层照搬到 W 模型的判定面：它的锚点已 17/17 在位，缺的只是拿基准去判定（机器分恒 0.000、追溯表 0/24）。交付形态是组合臂（两种方法叠在同一次运行），作新增格子而不替换阶段键——历史 81 个格子的归因靠这个键存续。

成本按 W 模型记 · 前置：先落机器分出处字段与两尺分列，否则它从约 0.39 掉到 0.000 会被读成「改造失败」
本轮扫清的三个静默失败前提

否则组合臂会自己把分数打成 0

① 相位写权按单个阶段算白名单 ⇒ 组合运行里另一种方法的合法交付物被拒收；已改成按组合阶段求并集。② 组合标记从不写进台账 ⇒ 组合格子与单范式格子在账面上完全同形（现役台账命中 0 行）；已补。③ 两套相位要求同时下发 ⇒ 失败时同时有两套解释；裁决规则写死：外部契约存在时以需求点清单为准，另一方只补测试线。

03c / Registered Endpoints

注册终点原样：每个范式只对它注册的终点打分。

口径写在 registration.json 里，跑之前锁死、跑完不能改口（paradigms.ts:10-15）。这一节保留终点定义，供上面每条场景结论对照。

DD 双钻
problem_coverage：问题空间是否被覆盖——需求里每个问题点有无对应实现、边界条件有没有做到。
PP 金字塔
plan_coverage：计划与结构是否覆盖。「结论先行」是它的子判据之一，不是注册终点——注册口径是 plan_coverage，比单独讲「结论前置」宽。
DP 设计方案引导编码
requirement_coverage：任务描述里的每一条需求是否被满足，逐条核，不靠「整体感觉」。当前唯一测出正效应的范式——人工判分尺 +0.153（剔除后 +0.214），同一批在机器判分尺上是 −0.167，两把尺符号相反，必须分开陈述（见上方场景一）。
VM W 模型
skips + rework：跳了几步、返工几次。两处口径注意：注册终点里没有「测试覆盖率」；且当前这两个指标是 executor 统计的 proxy 口径，不是工作流历史真值。它的机器判分尺恒 0.000，所以账面分数差全部来自人工判分。
CD CRISP-DM
analysis_validity：分析过程是否成立。数据泄漏与可复现是它的子判据，不是它的全部——打分打的是有效性整体，两条子判据各自还有守卫。
04 / Judge Accuracy

评判准确性：judge 自己也得被评测。

如果 judge 会漂、会漏、会编，所有分数都不可信。但 judge 本身是 LLM 调用，不是纯函数——所以要靠守卫与实测漂移来管住它，而不是宣称它天然稳定。

judge 的真实形态

LLM-as-judge，不是零 IO

评分走异步 worker，await callModelFn(...) 真发网络调用（eval-agent.ts:111）。确定性的部分是判据、权重、守卫和回退面，不是 judge 函数本身。

26-check 守卫

四类静默缺陷

judge 完整性测试实数 26 项 check（tests/paradigm-ab-judge-integrity.test.ts），覆盖「分数缺失、理由为空、锚点不存在、阶段跳过」；缺一项就不出分。

残片守卫

防「看起来有分，其实是垃圾」

截断、空证据、错位锚点、越界分数四类残片各有对应检查项，与 26-check 同属一条守卫链，不静默放行。

跨 judge 漂移实测

0 / −0.01 / +0.15 / 0

同批任务换 judge 重跑 4 个 cell：dp-007 双臂漂移 ≤0.01（稳健），vm-018/c 低分端 +0.15（偏严）。诚实边界：n=4，只能说明方向，不能声称全局 ≤0.01。

轮帽

复审 32 轮 / 初审 80 轮

PARADIGM_AB_REREVIEW_CEILING = 32（初审帽 80）。实测识别出 16 / 76 个 reviewer ≥60 轮的失控样本，纳入治理口径但没有剔除——真实失败样本要保留。

教训

首跑 12 cell 中 4 个假收敛

dp-001/t（147 轮重复）、vm-017/c（238 轮强制写入）、dp-015/t（837 轮撞 max-turns）、cd-eval/t（48 轮）——「看起来收敛」不等于收敛，这条教训直接催生了上面的守卫。

05 / Goals

三层评测目标。

评测要回答三个层次的问题：跑不跑得动、跑得对不对、跑得值不值。

可用性
跑得动：任务能进沙箱、能出结果、能在超时内完成；这是及格线，不是目标。
正确性
跑得对：各范式的注册终点（problem / plan / requirement coverage、skips+rework、analysis_validity）达标；正确性不能被「效率」换掉。
价值
跑得值：在正确的前提下，成本、时延、返工率是否可接受；这层决定能不能规模化。

实测结论
收益是场景相关的，不是「注入就更好」：全量池化平均差 −0.015；DP 在契约化交付上 +0.153（剔除 6 个作废格子后升到 +0.214，污染量 +0.061 且方向对 DP 有利，所以 +0.153 是保守值；它同时是最便宜的正效应 +100,035 tokens／对）；VM 平均 −0.007 却最贵（+2,646,958 tokens／对）、机器分尺恒 0.000；PP 与 DD 在短任务／探索任务上均为负。但每个范式只有 6–7 对配对样本——这是方向性信号，不是可推广结论。
两把尺
人工判分与机器判分必须分列陈述：DP 上两把尺符号相反（+0.153 vs −0.167）；机器分的可追认性只有 57.4%（112 行里 48 行对不上任何一代机器分文件），所以「切到机器分」这件事本身要先补出处字段。
口径注意
跳步 / rework 现在是 proxy 口径；把它们变成工作流历史真值的改造方案已写好（PR E0–E3），尚未落地。这一页把它列成待办，而不是成果。
统计纪律
门槛在开跑前锁定：α=0.05、功效 0.8、最小效应 d=0.5 ⇒ 约 60 对；实测剔除率约 50%，所以留了余量。五个阶段同时检验不校正，「至少撞上一次显著」的概率约 23% ⇒ 用 Holm。详见 心得页第 05 节。
