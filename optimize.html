Optimize / 优化方案

优化不是调参，
是改结构。

长任务系统的瓶颈，很少是「模型不够强」，更多是控制流绕、上下文乱、成本失控、改动危险。四个方向，对应四类结构性问题。

01 / Control Flow

控制流快路径。

先让「不该跑的」不跑、「该停的」早停、「能并的」并起来、「该断的」断干净。

熔断

连续失败就停

同类失败连续出现时熔断，避免在错误方向上持续烧钱；熔断状态可观测、可手动恢复。

重试

有上限、有退避

只对「可重试错误」重试，最多 2 次；每次重试保留上下文，不从头再来。

并发

能并的并

无依赖的子任务并发执行；有依赖的按拓扑序排队，不盲目并发导致互相踩踏。

取消

该断就断

用户取消、超时、上游失败时，向下传播取消信号，释放沙箱与配额，不留僵尸任务。

02 / Context

上下文管理。

上下文不是越多越好，而是「在对的时候给对的那一段」。三级降级 + 拓扑排序 + 分层共享。

三级降级
完整 → 摘要 → 锚点：窗口够就全给，不够就摘要，再不够就只给「关键行 + 文件指针」，保证不崩。
拓扑排序
按依赖关系组织上下文：先给被依赖的模块，再给调用方，模型读到的顺序就是它该思考的顺序。
分层共享
公共上下文（项目约定、接口契约）在多个 Agent 间共享一份，避免每个 Agent 重复读一遍、重复烧 token。
03 / Cost

成本工程。

成本不是「省 token」，是「让每一分钱都花在会改变结果的地方」。

缓存

命中比省更值钱

相同子任务、相同上下文指纹直接复用结果；缓存键带版本，避免旧结果污染新任务。

批处理

把碎请求合并

同质的小请求合并成批，减少往返与重复上下文；批量失败可单独重试。

蒸馏

用小模型干粗活

分类、抽取、格式化交给小模型；只有真正需要推理的步骤才上大模型。

预算

每个任务有上限

任务级 token / 时间 / 调用次数预算，超预算先降级再熔断，不让单任务拖垮整体。

04 / Discipline

工程纪律。

优化最怕「越改越乱」。四条纪律，保证每次改动都可解释、可回滚。

最小改动
一次只改一个变量，改完立刻验证；不把「重构 + 调优 + 新功能」混在一个提交里。
关注点分离
执行、评测、可观测各自独立；优化执行不碰评测逻辑，优化评测不改执行代码。
可回滚
每个优化都留回滚点；回滚后自动对比指标，确认「退回去确实更好」。
失败日志
失败必须留下「当时在干什么、输入是什么、错在哪」；没有失败日志的优化等于没做。

先把结构改对，再谈参数。结构不对，调参只是把错误调得更快。
