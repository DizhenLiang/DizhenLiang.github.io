Optimize / 优化方案

优化不是调参，
是改结构。

长任务系统的瓶颈，很少是「模型不够强」，更多是控制流绕、上下文乱、成本失控、固定开销大、改动危险。五个方向，对应五类结构性问题。

01 / Control Flow

控制流快路径。

先让「不该跑的」不跑、「该停的」早停、「能并的」并起来、「该断的」断干净。四个方向的真实形态与阈值都在下面，按代码里的值写。

熔断

看板派发器默认连续 2 次

同类失败连续出现即停，避免在错误方向上继续烧钱。DEFAULT_FAILURE_LIMIT = 2（hermes-kanban/constants.ts:99），可被 per-task 上限覆盖。注意它护的是派发链路，不是每个执行环节都有熔断。

重试

分级：核心 run 干脆不重试

核心 piRun 是 maximumAttempts = 1——不重发，靠 Workflow 重放 + workflowId 幂等键恢复；agentLoop / Plan-Execute-Review 是 3 次指数退避，cron 2 次。重试是步级重放：transcript 由 workflow 累积，单个失败步本身从头再发。

并发

Kahn 拓扑分层扇出——已实现，还没被真实请求走到

计划按依赖做拓扑分层（shared/topo-sort.ts:31,85、plan-layers.ts），同层用 child workflow Promise.all 并行扇出、跨层排队，不盲目并发互相踩踏。诚实边界：这两个模块在 src/ 的唯一引用方是 planExecuteReview.ts:63,296。那条形态 2026-11-02 起会由入口路由按判定起跑，但扇出还要 planner 交出带依赖边的多动作计划才会发生——实测那次运行的两步 planner 决策都是 done（空答复、零动作），所以分层扇出至今仍是「已实现、未被真实请求走到」，不是线上在跑的并发面。

取消

信号贯通，回收靠 GC

handle.cancel() → activity 的 cancellationSignal → interruptAcpProvider，取消能真正打断在跑的一步（activities/piAgent.ts:96,128-138）。诚实边界：工作区不是取消即回收，靠 workspace-gc.mts 清理，且它默认 dry-run。

02 / Context

上下文管理。

上下文不是越多越好，而是「在对的时候给对的那一段」。我做的是两级窗口 + 截断回读；并不存在一个「完整 → 摘要 → 锚点」的三档降级开关，别按那个名字找代码。

两级窗口 + 截断回读
超窗时保留头尾、中段替换成摘要（[head + summary + tail]，pi-agent-compaction.ts:103-164；拿不到摘要就原样放行），prompt 侧再留「关键行 + 你自己去读文件」的回捞指针（prompt-builder.ts:480-499）。L1 窗口策略目前只有 legacy ↔ jev-node 两档实验位（l1-window-scheme.ts:2-13）。
拓扑排序的真实用途
它排的是执行层的并发顺序（哪些步骤同层可并行），不是喂给模型的阅读顺序——这两件事容易被讲成一件。当前它只挂在零流量那条形态上，所以上面写「已实现、未被走到」。
单份事实源
项目上下文单份落盘（.apex-agent/project-context + context-dag），每次请求现读 3 个文件、被多个路由复用（project-context.ts:573-592）。边界：没有跨 Agent 的上下文缓存或去重，所以是「一份事实源被多处复用」，不是「共享上下文省 token」。
03 / Cost

成本工程。

成本不是「省 token」，是「让每一分钱都花在会改变结果的地方」。

缓存

工具结果按参数指纹复用

缓存键 tool:${toolName}:${argsHash} + TTL（harness-postgres.ts:576,659），另有命中率指标（production-metrics.ts:151）。已知短板：缓存键没有版本位，schema 变更后旧结果可能被复用——记在待办里，不是已解决。

批处理

真实生效的只有两处

embedding 批量池化（embed-pool.ts:58、fastembed-service.ts:237-287）与 ES _bulk 200 条/批（elasticsearch-client.ts:210）。边界：LLM 侧「同质小请求合批」没有实现，只有上面这两条路径真在批处理。

模型分层

三张座位各配各的模型，缺省仍是同一个

真实机制是角色化模型槽与 fallback 链（model-orchestration.ts:78-84），小模型只用在检索改写等辅助槽。2026-11-03 更正我上一版的口径：座位模型已由两张扩到三张——APEX_SEAT_MODEL_PLANNER（规划器）/ APEX_SEAT_MODEL_EXECUTER（执行器）/ APEX_SEAT_MODEL_REVIEWER（评审器），见 src/lib/router/seat-models.ts，执行器现在有自己的模型槽。此前那句「执行器压根没有模型槽是实测事实」只对 plan 臂成立：那里的执行步（planExecuteReview.ts:202-246 的 runOneAction）是确定性副作用派发、本来就不发模型请求；模型驱动的执行只在 agent 臂那条循环里。另一半同样要说清：座位不只配了模型，还带角色名（SEAT_WORKER_ROLE → Manager / Executor / Critique），agent 臂默认就把执行器的 RoleSpec 注进决策提示词——这一处不是缺省不变形，是默认开启的提示词变更。边界：三个 env 都不配 ⇒ 座位字段一个都不进 INPUT、模型沿用本次 run 的；「分类走小模型、推理走大模型」那种自动判据还不存在，现在是人来配，不是系统来判。

预算

轮次与时间帽在跑，token 帽在休眠件里

线上实跑的是轮次帽（pi-agent-loop-guard.ts:42,177-237）与时间上限（pi-agent-runner.ts:856,974），超了就早停或抛错，没有「先降级再熔断」那条链。诚实边界：tokenBudget 早停写在 planner-executor.ts:92,217-227 的双智能体编排类里，而该类全仓 new 计数为 0——它是休眠件，我不把它算成在跑的预算面。

04 / Structure

结构降本：工作区平面与空闲运行时。

这两块的开销不是「模型贵」，是结构贵：每个任务一份干净工作区、每个空闲会话一个常驻执行体。下面每个毫秒都能在本机复算，也带着把它限制住的边界——把倍数写成「线上已兑现的收益」是我不做的事。

工作区 provider

先证逐字节等价，再谈 ×214

把「工作区」抽象成一个接口（mount / read / write / list / commit / unmount，src/lib/workspace/），三后端并存：git-worktree（保留作回退基线）、overlay（LayerFS 语义、无 FUSE）、layerfs（真实适配器，缺依赖就类型化报错、不静默降级）。在真实仓库（5,305 个跟踪文件）先证逐字节等价（PARITY_OK、diffs = []），再量差：挂载 28ms vs 64,864ms（×2,317）· 卸载 92ms vs 165,691ms（×1,801）· 全链路 1,132ms vs 242,111ms（×214）。诚实边界：默认执行路径仍是 git-worktree；overlay 目前只被评测 harness 直接消费（PARADIGM_AB_WORKSPACE=overlay），而 resolveProvider 在 src/ 与 scripts/ 零调用方 ⇒ 这是「选项已备好」，不是「线上已切换」。

LayerFS 在本机跑通

建/拆便宜三个数量级，每一次文件访问贵 240 倍

自建 sealed bundle 把 LayerFS 真跑起来（Windows 驱动 → WSL2 worker → 容器内 FUSE）：真实仓库一轮 fork + mount + unmount ≈45–260ms，对照同仓 worktree 建拆 ≈230,555ms；一次性导入 5,327 个文件 = 132s，一轮即回本。同一批实测也把反面量了：每次文件操作经 Sandbox exec 的容器往返税中位 240ms，而宿主直读同一批文件中位 1ms ⇒ 结论是「优化建/拆，代价是每一次访问」，划算与否取决于这个 run 动多少文件，不是无条件更快。跨界另有两条硬上限（exec stdout 按 1MiB 分页、Linux 单参数 128KiB）⇒ 读要窗口循环、写要分块并对账落盘尺寸。还有一条会静默判错的坑：capabilities.hostPath === false，返回的根路径是容器内路径，评测 harness 因此显式拒绝 =layerfs——把它当宿主 cwd 去 grading 会读错树。

空闲挂起运行时

没有「挂起」这个动作：队列空 ⇒ 无常驻 driver

移植自 infinity 的 agent_scale.rs（src/lib/agent-runtime/，1,042 行）：每线程一个输入队列、driver 惰性起、状态只在 store、事件走有界环形缓冲。核心性质不是「省了多少内存」，而是队列空 ⇒ 一个 driver 都不驻留——挂起是默认态，唤醒才是异常态。它由 12 项守卫直接断言 residentDrivers === 0（40 线程 × 4 轮之后归零），不靠内存读数推断；并补上示例不需要而生产必须的四条：单飞、有界队列背压、轮转公平、优雅关停与错误隔离。

规模实测

空闲近乎不要钱，价目表上那一格是唤醒

npm run eval:agent:scale（2026-11-03 本机，2000 agent × 5 轮合成回显负载）两种配置都测：历史在内存态 10,000 轮 0.7s 跑完、idle 常驻 17.8 KiB/agent、冷唤醒均值 72ms；历史落盘（JSONL）态 idle RSS 49.3MiB，反而低于 63.7MiB 基线——空闲净成本≈0，代价是冷唤醒均值 8.36s（磁盘 + 单飞排队）。测两种是故意的：内存态里历史从没离开 RAM，所谓「挂起释放内存」在那个配置下就是个假数。

判定要走到执行面才算数——但要说清哪一层走到了
路由之外，2026-11-03 落了三件事，进度并不同步，别混成一句「执行面已接」或「都没接」：
① 座位模型 + 角色名已进入口（src/lib/router/seat-models.ts）：APEX_SEAT_MODEL_PLANNER / _EXECUTER / _REVIEWER 在入口读 env，以 planModel / reviewModel（plan 臂）与 model（agent 臂）进 workflow INPUT——不在工作流里读 env（沙箱违例，且宿主与 worker 容器档位不同 ⇒ 重放可能翻成另一个模型），continueAsNew 用 ...input 展开自动携带；env 不配 ⇒ 字段不进 INPUT、模型沿用本次 run 的。但角色名 role: "Executor" 是无条件带的，于是 agentStep.ts:385 默认就把执行器 RoleSpec 注进决策提示词——这一处缺省不是零变化。
② 建项目派发层已接线、门缺省关：src/lib/router/provision.ts 用既有六步 helper 建项目并把本轮会话绑上（项目键取自消息的幂等种子 sha256 ⇒ 同一句话重跑派同一个键；失败以 { ok: false } 返回、绝不抛出），由分诊管线 src/lib/feeds/task-pipeline.ts:217 在 new_project 判定上调用，门 APEX_ROUTER_AUTO_CREATE_PROJECT 缺省关 ⇒ 关时判定只写进任务体、活仍留在给定项目里。
③ worker 生命周期目前只有判定：纯函数三选一 answer_only | maintain | spawn（src/lib/router/worker-lifecycle.ts:72，8 项测试）——内容没变 = 不起 worker，同一张座位已挂着就维持（重复起跑 = 重复付费 + 重复写）；模型只参与「要几张座位」，不参与「要不要起」。边界：decideWorkerLifecycle 除自身测试外零生产消费方，起跑派发函数 dispatchProjectWorkers 全仓零定义 ⇒ worker 那一面还没接到执行；真工作流证据 tests/temporal-seat-dispatch.integration.ts（createLocal 起临时 dev server、活动全 mock、不需要 Docker）目前不在 GUARDS 的 77 条里，不进 npm run verify，要手动 npx tsx 跑；改动要吃进容器化 worker 仍需 bundle 重建 + 进程重启，而本机 Docker 引擎当前起不来（dev 侧 tsx 直跑源码，重起即生效）。
两个会静默吃掉收益的缺陷
① git worktree add 中途被杀留下 locked initializing 注册，此后 git worktree prune 永远跳过它——目录早没了、注册不可回收，本仓曾累积 354 条注册 / 约 29 GiB；已修：挂载前先 unlock + prune。② store 放进仓库内会抵消全部收益：同一个删除动作，仓库内 4,998ms、系统临时目录 93ms（仓库被索引器与杀软盯着）；已修：cell 的 store 默认落系统临时目录（APEX_WORKSPACE_STORE 可覆盖）。
口径
这些数都是本机实测，且是混合文件系统口径：LayerFS 的数字在 WSL2 ext4 内、源树经 9P 读入，git 对照的数字在 NTFS 上由 Windows git 做，合成树（2,001 文件）也小于本仓（5,305 文件）⇒ 方向与量级可信，绝对值不可跨表相减。
05 / Discipline

工程纪律。

优化最怕「越改越乱」。这四条是我实际遵守的工作纪律（不是系统机制），所以写成习惯而不是功能。

最小改动
一次只改一个变量，改完立刻验证；不把「重构 + 调优 + 新功能」混在一个提交里。
关注点分离
执行、评测、可观测各自独立；优化执行不碰评测逻辑，优化评测不改执行代码——评测口径一改，历史批次就不可比了。
可回滚
每个优化留回滚点（分支 + 旗标）；回滚后是我人工对比指标，自动对比还没做——这一条目前靠人，不靠机制。
失败日志
失败必须留下「当时在干什么、输入是什么、错在哪」；没有失败日志的优化等于没做。

先把结构改对，再谈参数。结构不对，调参只是把错误调得更快。
