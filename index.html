The Facility / 整套设施

不是一套代码，是一台机器。

Apex-Agent 把「长任务」跑成「产品」：任务定义、沙箱执行、执行权威、评测与数据回流咬合成一个可自我改进的飞轮。下面五张卡都能在源码里指到位置。

01 / 飞轮

任务定义 → 隔离执行 → 智能体跑完 → 独立评测 → 数据回流

每一轮都把「失败」变成下一轮的「数据」。评测里发现的假收敛，直接变成下一批的守卫项——不是一次性脚本，是持续收口的循环。

38 任务 × 2 臂 = 76 条轨迹
02 / 隔离执行

OpenSandbox 容器沙箱 + 只读评测工具环

智能体生成的代码跑在容器沙箱里，sandboxed 控制面默认 gVisor（runsc），runc / docker 备援，可选 E2B 微 VM。评测执行另走一条只读、限定 cwd、断网的 worktree 工具环，不碰生产 workflow。

执行 / 评测 两面分离
03 / 兜底与巡检

重放 · 幂等 · 巡检 · 熔断

核心 run 靠 Workflow 重放 + 幂等键而不是盲重试；卡死由 claim TTL / 心跳陈旧 / 崩溃检测 + Temporal 超时收口，worker 进程另有 watchdog 保活重拉。26 项 judge 完整性守卫 + 76 条 test:guards（scripts/run-guards.mjs 的 GUARDS 数组，可数）把「静默错误」提前暴露。

看板熔断默认连续 2 次 · test:fault-injection 串跑 5 个测试
04 / 可观测

指标推送 + 时序 + 追踪，全链路批次 tag

Pushgateway 推指标、Prometheus 存时序、Langfuse 记 trace 与评分；每条轨迹带批次 tag，异常 fail-loud 不静默。Grafana 面板已退役，采集与查询层保留。

可回放 · 可定位 · 可审计

By the numbers / 事实

用数字说话。

四个数都能在仓库里复算，并写清各自口径：哪些是提交量、哪些是行数、哪些是评测轨迹。口径写清楚，比数字大更要紧。

口径
1,211 是提交数不是任务数，真实跑过的唯一任务 38 个。258,283 是代码行数，不是测试执行次数：git 跟踪的测试文件 162 个（*.test.ts/.tsx/.mts），用例声明 990 条。行数必须单遍求和——用 xargs wc -l | tail -1 会因参数被拆成多段而只数到最后一批，同一范围实测只剩 71,506；数字没核对过求和方式，就等于没核对过。
行数≠格子数
两份结果台账合计 206 行，按「任务 × 臂 × 批次」去重后只有 81 个格子，重复率 154.3%。10-30 那份「76/76 全有判分、零缺口」的结论，就是数了行、宣布了格子、中间漏了去重。台账还没有运行标识列，实测 4 / 81 个格子的两次运行塌缩成一行。
本轮新增
2026-11-02 把两条分工写成了代码与守卫：提示词装配顺序固定为角色段 → 任务正文 → 上游输入，以及相位写权——计划与审查角色不能改动执行者的交付本体，缺陷以 REWORK 行回流。29 项检查跑绿，并用 8 种改坏证明它真的会变红。
未落地
81 个任务里 41 个从未执行，这是配对数不足的唯一根因；组合范式臂（把两种方法叠在同一次运行）至今 0 行入账，本轮只修掉了它三个会静默失败的前提；跳步 / 返工仍是执行段自报的 proxy 口径；动态路由 96% 停在只记录不生效的影子模式。跨 judge 漂移实测：dp-007 双臂 ≤0.01，最大 +0.15（n=4）。
