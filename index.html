数据管线设施

一套可复现的评测数据管线

评测不是跑一次脚本，而是一条可重放的数据管线：任务打包、独立执行、指标落盘、台账可追溯。

  • Harbor 任务格式 — 任务打包 + record/replay，评测可重放
  • 独立 eval 队列 — apex-eval task queue + 独立 schema，不触生产
  • 指标三平面 — Pushgateway（harborEval*）+ Prometheus + Langfuse
  • 驱动与分析 — eval skeleton + registration.json + analyze.ipynb
  • 批次治理 — 批次 tag + fail-loud，缺臂 / 污染直接踢出
  • 可追溯台账 — 191 行，每个结论能回到批次 / 臂 / trace
评测标准

金标准 + 五阶段 rubric

金标准不是「模型会不会做题」，而是「模型经 harness 能否复现 Apex 生产级框架（可观测 / 可审计 / 可复现 / 持久）」。

  • DD 双钻 — 问题空间覆盖、方案多样性、是否过早锁定
  • PP 金字塔 — 结论是否前置、分层清晰度、可扫读性
  • DP 设计方案 — 需求覆盖、与 DP 一致性、Harbor 合规
  • VM V 模型 — 覆盖率、rework、跳步、缺陷逃逸、首次正确率
  • CD CRISP-DM — 分析有效性、数据泄漏、业务理解、可复现
  • rubric 锚点 — 结构门 + 覆盖点，每条锚到真实工件 file:line
评判准确性

让 judge 本身可验证

判分如果「不报错只悄悄错」，分数就不可信。所以 judge 自己也要被测试、被校准、被纠错。

  • 零 IO 纯函数 — score(prompt,output)→Verdict，可单测
  • 22-check 守卫 — 空 verdict、越界分、覆盖旧 verdict、台账未落盘
  • 四道残片守卫 — landing 存在 / 非空 / 校验和 / score 已写
  • 跨 judge 漂移 ≤0.01 — 同一工件换 judge 复评，分数稳定
  • 失控剔除 — reviewer 轮帽 32，16/76 失控复审被识别并剔除
  • 首跑 4/12 假收敛 — 正是这次教训，把「分数可信」做成质量基线
一条永远不会失败的断言，不是测试，是装饰。

所以关键不变量都用「会变红的守卫」钉住：投影不许双写、工作流体不读环境变量、工具调用不许漏登记——改坏源码，断言必须真的失败。
