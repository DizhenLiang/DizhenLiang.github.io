它说任务
跑完了。我没信。

我做 Apex-Agent 的起点不是"让智能体更聪明"，而是"让它说的话能被验证"。一个跑完长任务的 agent 会告诉你它交付了三个文件——而仓库里一个字节都没变。这套设施就是为了对付这句话：执行交给不会说谎的权威，判分交给会变红的守卫，结论交给能被我自己复算的脚本。

The Spine / 一条线

四幕。每一幕的每个数字都能当场复算，取证口径收在正文下面的「证据」抽屉里——正文负责让人读下去，抽屉负责让人问到底。

I不信任

问题不是它跑不完，是它报完成。

第一批长任务跑下来，最刺眼的不是失败，是成功的样子：agent 在最后一轮写了一段漂亮的交付说明，状态机记成 final，评分给了分。我去看工作区——文件是空的。它没有撒谎的动机，它只是没人要求它为自己说的话负责。

所以第一刀不砍在模型上，砍在契约上：宣称有交付物而写入台账里零落盘，就不许报成功。这条后来变成评测里最硬的一格——不是提示词里多写一句"请诚实"，是结构上不给它说谎的位置。

同一条逻辑往外推，就推到了整个系统的形状：既然自我陈述不可信，那"发生过什么"必须由一个不依赖陈述者的东西来定。

证据 · 落盘强制门与它的来历

final 阶段四道残片守卫（截断 / 空证据 / 错位锚点 / 越界分数）断掉「假 final → 零落盘 → reward 0」连锁；交付清单与落地审计（landing audit）共用同一套路径解析 ⇒ 门与审计永不漂移。评测面实测：无落盘一票否决 0 分，破坏性重写封顶 0.5。

代价与被抓住的样本也是量出来的：复审失控取证到 cell 级（dp-008/c reviewer 162 轮里 86 轮 deny/replay 且零升级出口）；复审轮帽 REREVIEW_CEILING=32，实测识别 16/76 个 reviewer ≥60 轮的失控样本，纳入治理口径但不剔除——真实失败样本要留着。

结构强制优于提示词祈祷的方法论见心得。

II交给权威

把"发生了什么"交给一个会重播的东西。

执行权威我选了 Temporal，不是因为它时髦，是因为它回答了我唯一关心的问题：崩溃之后，系统还记不记得真实发生过什么。它的 History 可以重放，所以副作用恰好一次、重复投递被幂等键吸收、长任务靠 continueAsNew（续跑）而不是靠运气。

顺手做了一次减法。队列层我评估过 bullmq（Redis 上的任务队列），最终没有采用——但它的名字在我自己的简历和面经里活了两个月，写成"承载派发"。2026-11-03 我按调用方计数把它从文档里清了个干净：src/ 里 bullmq 命中数为 0，那个手写的 Redis Streams 完成队列调用方也是 0。Redis 一条能力都没动，只是回到它真正在做的事：缓存、限流、会话、凭证池、分布式锁、跨进程缓存失效。

至于 PG，它被从"事实源"降级成"可以从 History 重建的读模型"，并且用四层卡口把唯一的写口锁死在一个文件里。绿只等于"没有字面量越权写"，不等于"已证明安全"——这句话我写进注释和 runbook，因为盲点也得是公开的。

证据 · 三层分治与单写权威（可当场追问）

入口：harness-bridge.publishTask → dispatchIngress（默认拒绝白名单，唯一接入点）→ startWorkflowIdempotent，无中间队列中转；Temporal 不可达则 fail-closed，不回退 PG。task queue（任务队列）apex-orchestrator / apex-side-effects 即传输 + 执行层。

调度面：平台 cron 没有进程内守护，执行面就是 Temporal Schedule——automation-scheduler.ts:224 client.schedule.create，action 指向 apexCronJobRun。2026-11-03 无 Docker 实测 worker 起来即 automation schedule reconcile: synced=1/1。

单写：TC-11 四层卡口 = 字面量/行扫描（正则命中 INSERT INTO|UPDATE (session_tree|activity_results)，出现在 projection/sync.ts 之外即红）+ import 边界扫描 + 运行时 fail-closed + worker 在场校验；5 个故障注入测试串跑（41 处断言）。

Kafka 的诚实位置：代码、compose、pm2 三条腿齐，但门在 harness-bridge.ts:27-28 要求 KAFKA_INGRESS_ENABLED==="true" 且 KAFKA_INGRESS_MODE==="kafka"，实测 .env 里 grep KAFKA 零命中 ⇒ 三道门全关，今天是旁路而非链路。2026-11-03 把「能翻成 on 之前必须先兑现」的三处补齐：① 生产侧真 fail-closed（此前 broker 挂了照样返回成功 ack），② 派生投影表 projection_activity_results 有人建（此前全仓只有写方没有建方 ⇒ 新库第一条投影就 42P01 进死信），③ 三段式编排进默认拒绝白名单并补上命令面腿（此前该类型会被「确认并丢弃」，看着像没有流量）。46 项守卫单跑 PASS 46 / FAIL 0；但运行时一格没翻，而且入库也只走了一步——② 的代码连同 runbook 进了提交，①③ 与并发会话的在飞改动交叉（git status 为 MM），守卫文件仍未跟踪 ⇒ 按提交纪律排队。边界写在 docs/kafka-runbook.md §7，含一条被探针证伪的自拟理由。

人在环信号：humanApproval（planExecuteReview.ts:92）与 agentHumanApproval（agentLoop.ts:79）在 src/ 零发送方——全仓唯一的 handle.signal( 在测试夹具里。处理器定义了，没人按。

III反噬

这套标准回过头，抓到我四次。

这是我最想让人看的部分，因为前面两幕说的是工程能力，这一幕说的是它对我也不留情面。四次里两次是我发布的数字，一次是我以为在跑其实根本没跑的东西，还有一次是文档活得比代码久。

台账写了 206 行，我说过「76/76 全有判分、零缺口」。按「任务 × 臂 × 批次」去重，只剩 81 个格子——重复率 154.3%。我数了行，宣布了格子，中间漏了去重

第二次是路由押的那一格。原文引用「+0.17，唯一实测正例」，出自一份已经不在仓库里的批次报告。我用现台账独立复算，得 +0.083（n=6 配对，p=0.625）——没过大显著性；而代价是实测的：注入 planner/reviewer 后 treatment 臂 prompt token +71%。引用作废，代码注释和对外文案同步改掉。这一幕的口径只有一句：机制被证明在跑，效果没有被证明。

第三次最险。我一直以为 worker（取活的进程）在跑，因为 :7233 端口在听。2026-11-03 判活脚本给我的是 pollers=0（零个取活线程）——workflow 全在静默排队等超时。查下去是个真断：一个 workflow 侧的 import 在打包时被 outbase（打包基准目录）抬出一级，指向了一个从来没被写过的目录，于是 worker 构建自那个提交之后就一直是坏的。修完之后同一道门变成 pollers=1, pollers=1。从这次起我定了条铁律：端口在听不是活着，判活只认 pollers。傍晚又给它补了一层——同一个端口可以有两个听众：公网位由 Docker 转发容器，环回位随时间换主人（跑 temporal 测试时会被 @temporalio/testing 的临时 dev server 抢走，环回优先）。所以判活除了认 pollers，还要认读数那一刻环回位的持有人（netstat 取 pid → tasklist 认进程）。那一次持有人是 wslrelay.exe，同一时刻从宿主读到 2 个活 poller —— 容器真的在取活，第一次拿到宿主侧的独立证据。

第四次就是上面那个 bullmq——注释、文档、我的简历都能声称它在服役，调用方计数说它不存在。注释只当线索，不当证据，这条现在写在方法论里。

证据 · 四次的复算入口

① 台账：两份合计 206 行 → 去重 81 格（主台账 198 行 = 76 格）；同批可配对 33 对，门槛 60 对未达 ⇒ 只报方向信号。合并 meanΔ −0.015（11 胜 / 15 负 / 7 平）；分尺读数符号相反：DP 在人工判分尺 +0.153、在机器判分尺 −0.167。台账尚无运行标识列，4 / 81 个格子的两次运行塌缩成同一行。

② 那一格：复算口径 = 按 任务×臂 去重取最新 seq + 精确符号翻转检验 + 取人工判分尺；权威分析文档另一口径 +0.150 / p=0.500 且自判"收益是单格伪影"。跨 judge 漂移：dp-007 双臂 ≤0.01，vm-018/c 低分端 +0.15（n=4，只报方向）。

③ worker：断点 src/lib/temporal/workflows/agentLoop.ts:35，引入提交 a186bb16，修复提交 e62ed56c（2026-11-03，只动 build 脚本 +9 行）；可行性先取证——被引的两个模块自身零 import（纯函数），且全仓 workflow 越出子树的 import 只有这一条，所以补一个目录是完备解。

④ 队列层：删除 redis-completion-queue.ts（252 行，src/ 调用方 0）与误名的 scripts/start-queue-worker.ts、死键 platform.queueEnabled；提交 ce322127（21 文件 +71/−310），复核 tsc 退出 0、8 文件 80 测试通过。

IV未竟

我知道自己停在哪，并且把它写进正文。

设施现在的真实形状是：执行面活着，判断面还在门槛外。要不要起一张工作座位，我已经写成纯函数（三选一：只答 / 维持 / 起新）并有测试；但那个判定除自身测试外没有生产消费方，起跑派发的函数全仓零定义 ⇒ 还没有真 worker 被它拉起。两条路由门都缺省 shadow（只记录、不改行为），动态路由 96% 的任务仍走全拓扑——那个"预估省 43%"是影子读数，不是已实现收益。

配对数不足也有唯一根因，不好听但清楚：81 个任务里 41 个从未执行。而这一切此刻还压在一种依赖上——现场地址不可达。2026-11-03 同一天量了两次，结论不同：早间 Docker 引擎无响应、数据库端口连测三次拒连，我把根因记在宿主页面的地基（要 4GB 的虚拟机，本机总量 7,103MB、实测可用 458MB）；午后复测引擎已经活着（四个基础设施容器全 healthy），可用内存反而只剩 253MB——"内存不够所以栈起不来"于是只能算相关，不算证明。站点仍不可达，但断点换了位置：本机 Web 面（:3000）没起，到 Vercel（前端托管的边缘）的连接被重置。同一个地址、两次实测指着两个断点，所以我把它写成两次，而不是挑一次讲成故事。

我不打算把这些藏进脚注。一份只讲做成的简历，和一台只会报成功的 agent，是同一种病。

证据 · 边界清单与口径（逐条可追）

未生效：动态路由 96% 影子模式，预估收益是影子读数；三段式 Plan-Execute-Review 自 2026-11-02 起由入口路由决定启不启动、两臂都有真实请求跑通，但它押的那格 +0.083 / p=0.625 未过显著性、代价 prompt token +71%、分档阈值 T_SIMPLE=30 未校准；planner→executor→reviewer 的写权拓扑仍只在评测 harness（src/ 零调用），生产侧 reviewer 是只读座位；四范式引擎 registry.json 已入库但总开关默认 enabled: false；预注册 k_per_task=3 从未执行、registration.json 的 locked_at 仍是 PRE-RUN ⇒ 当前所有 p 值与 promote 级结论无效。

结构收益 ≠ 线上收益：工作区三后端里默认执行路径仍是 git-worktree，overlay 只被评测 harness 直接消费，resolveProvider 与 agent-runtime 在 src/+scripts/ 零生产调用方。实测倍数（本地）：全链路 1,132ms vs 242,111ms（×214）；空闲挂起运行时 2000 agent × 5 轮，idle 常驻 17.8 KiB/agent、冷唤醒 72ms，落盘态 idle RSS 49.3MiB < 63.7MiB 基线、代价冷唤醒均值 8.36s。同一批实测也量了反面：每次文件操作经容器 exec 中位 240ms，宿主直读同一批文件中位 1ms ⇒ 便宜的是建/拆，贵的是每一次访问。

卫生项：台账写入仍是就地覆写（无锁、无 temp+rename），消费者可读到中间态，已列为待修；:7233 上现在挂的是评测用临时 dev server，不是生产 Temporal，别按端口臆断现场可达。

守卫会长，所以数值得带日期：2026-11-03 实测 test:guards 78 条（同日早间读数 77——清单当天在长）；仓内记录的最近一次全量实跑 67/68（那份记录时清单是 68 条——分母跟着清单长，两个数得一起看）。

The Machine / 幕后的机器

四幕背后，是一台能自己收口的机器。

故事讲的是一次次转弯，转弯能发生是因为底下有东西在兜。四块都能在源码里指到位置。

01 / 飞轮

失败不是事故，是下一轮的输入

任务定义 → 隔离执行 → 跑完 → 独立评判 → 数据回流。评测里发现的假收敛，直接变成下一批的守卫项；判分自己也被判过——跨 judge 漂移量出来了就写进口径，不靠"应该没问题"。

38 任务 × 2 臂 = 76 条轨迹 · 台账去重后 81 格
02 / 隔离

让代码无处可逃，也让评测碰不到生产

智能体生成的代码跑在容器沙箱里，控制面默认 gVisor（runsc），runc / docker 备援，可选 E2B 微 VM。评测执行另走一条只读、限定 cwd、断网的 worktree 工具环——执行面与评判面天生分离。

执行 / 评判 两面分离
03 / 收口

卡死、重复、静默错，各有专门的东西接住

核心 run 靠重放 + 幂等键而不是盲重试；卡死由 claim TTL / 心跳陈旧 / 崩溃检测 + Temporal 超时收口，worker 另有 watchdog（看门狗）重拉。判活只认 pollers，不认端口——这条是 III 幕那次教训换来的。

26 项 judge 完整性守卫 · 78 条 test:guards · 熔断默认连续 2 次
04 / 可观测

每条轨迹带批次 tag，异常不许安静

Pushgateway 推指标、Prometheus 存时序、Langfuse 记 trace 与评分，三平面隔离所以批次互不串味。缺臂、污染样本触发 fail-loud（响亮失败）直接踢出，而不是留在台账里冒充结论。Grafana 面板已退役，采集与查询层保留。
